# 6. Алгоритмы работы системы

Раздел описывает, как система обрабатывает запросы и данные. Требования разделов 2 и 5 определяют,
*что* видит пользователь; этот раздел — *как* система должна это обеспечивать.

## 6.1. Обработка HTTP-запроса

Каждый запрос проходит одну и ту же цепочку. Порядок промежуточных слоёв (middleware) фиксирован в `settings.py`:

| № | Слой | Действие при запросе | Действие при ответе |
| --- | --- | --- | --- |
| 1 | `SecurityMiddleware` | базовые проверки безопасности | заголовки безопасности (`X-Content-Type-Options: nosniff` и др.) |
| 2 | `SessionMiddleware` | читает cookie `sessionid`; данные сессии загружаются из БД при первом обращении | сохраняет изменённую сессию, выставляет cookie |
| 3 | `CommonMiddleware` | проверяет заголовок `Host` по `ALLOWED_HOSTS` (иначе 400); добавляет завершающий `/` к адресу | — |
| 4 | `CsrfViewMiddleware` | для POST сверяет CSRF-токен формы с cookie `csrftoken` (иначе 403, страница Э11) | выставляет cookie `csrftoken` |
| 5 | `AuthenticationMiddleware` | определяет `request.user` по сессии (гость, если сессии нет) | — |
| 6 | `MessageMiddleware` | загружает одноразовые сообщения | сохраняет новые сообщения до следующего запроса |
| 7 | `XFrameOptionsMiddleware` | — | `X-Frame-Options: DENY` (страницы нельзя встроить во фрейм) |
| 8 | `DatabaseUnavailableMiddleware` | — | при ошибке подключения к БД заменяет ответ страницей Э9 (6.6) |

Язык интерфейса фиксирован — русский (`LANGUAGE_CODE = "ru"`) и не зависит от языка браузера
(заголовок `Accept-Language` не учитывается).

Далее:

1. Маршрутизатор (`medtracker/urls.py` → `analyses/urls.py`) находит представление по адресу; адрес не найден → 404.
2. Открывается транзакция БД (`ATOMIC_REQUESTS = True`) — всё, что представление запишет в БД, фиксируется
   одной транзакцией в конце обработки или откатывается целиком при исключении.
3. Представление проверяет доступ (6.2), обрабатывает форму (6.3) и готовит данные для шаблона.
4. Шаблон формирует HTML; ответ проходит слои в обратном порядке и отправляется браузеру.

## 6.2. Проверка доступа

Для каждого запроса к функциям разделов 2.2–2.3:

```text
1. request.user — гость?
      да  → 302 на /accounts/login/?next=<текущий адрес>            (FR-4)
2. Адрес содержит идентификатор объекта (<id>)?
      да  → объект ищется запросом с условием владельца:
              анализ:   Analysis.objects.filter(user=request.user).get(pk=id)
              значение: AnalysisValue.objects.filter(analysis__user=request.user).get(pk=id)
            не найден (нет такого id ИЛИ чужой) → 404                (FR-5)
3. Форма содержит ссылку на анализ (поле «Анализ»)?
      да  → список допустимых значений = анализы текущего пользователя;
            значение вне списка → ошибка поля «Выберите корректный вариант...»
4. Выполнить операцию.
```

Так как чужой объект и несуществующий объект обрабатываются одинаково, по ответу нельзя узнать,
существует ли объект с данным идентификатором у другого пользователя.

Доступ к `/admin/` проверяется модулем `django.contrib.admin`: требуется `is_active` и `is_staff`.

## 6.3. Алгоритмы операций

### 6.3.1. Список анализов (FR-6, FR-7)

Один SQL-запрос: выборка анализов пользователя с присоединением единицы и подсчётом значений.

```sql
SELECT a.*, u.*, COUNT(v.id) AS values_count
FROM analyses_analysis a
LEFT JOIN analyses_unit u          ON u.id = a.unit_id
LEFT JOIN analyses_analysisvalue v ON v.analysis_id = a.id
WHERE a.user_id = :user_id
  [AND UPPER(a.name) LIKE UPPER('%' || :q || '%')]   -- только при непустом q
GROUP BY a.id, u.id
ORDER BY a.name;
```

Сравнение `UPPER(...) LIKE UPPER(...)` в PostgreSQL корректно работает с кириллицей.

### 6.3.2. Страница анализа и постраничный вывод (FR-9, FR-12)

```text
1. Получить анализ с проверкой владельца (6.2) и единицей — 1 запрос.
2. N = COUNT(значений анализа) — 1 запрос.
3. M = max(1, ceil(N / 50)) — число страниц.
4. p = параметр page:
      не число        → p = 1
      p < 1 или p > M → p = M
5. Выбрать значения: ORDER BY measured_at DESC LIMIT 50 OFFSET (p − 1) × 50 — 1 запрос.
6. Навигация: «← Новее» если p > 1; «Старее →» если p < M; выводится только при M > 1.
```

Итого 3 запроса к таблицам предметной области независимо от числа значений.

### 6.3.3. Создание и изменение анализа (FR-8, FR-10)

```text
1. Очистить поля от пробелов по краям.
2. Проверить обязательность и длину (название ≤ 128, описание ≤ 2000).
3. Проверить уникальность:
      существует ли анализ этого пользователя с UPPER(name) = UPPER(:name)
      [и id ≠ id изменяемого анализа]
      да → ошибка «Анализ с таким названием уже существует.»
4. Сохранить. Владелец = request.user (только при создании; при изменении владелец не меняется).
      created_at = now() при создании; updated_at = now() при каждом сохранении.
```

Дополнительно в БД действует ограничение уникальности `uq_analysis_user_name_ci` по (`LOWER(name)`, `user_id`):
если два запроса одновременно пройдут шаг 3, второй INSERT будет отклонён СУБД и транзакция откатится.

### 6.3.4. Создание и изменение значения (FR-13, FR-14)

```text
1. Список анализов для поля «Анализ» = анализы request.user ORDER BY name.
2. Проверить поля; значение и комментарий очистить от пробелов по краям.
3. Разобрать «Дата и время сдачи» в формате ГГГГ-ММ-ДДTЧЧ:ММ как время Europe/Moscow.
4. Если measured_at > текущий момент → ошибка «Дата сдачи не может быть в будущем.»
5. Сохранить; measured_at хранится в UTC.
6. Перенаправить на страницу анализа, указанного в значении после сохранения.
```

При открытии формы добавления поле даты заполняется текущими датой и временем (Europe/Moscow)
с обнулёнными секундами.

### 6.3.5. Удаление (FR-11, FR-15)

- GET — только показ страницы подтверждения, данные не изменяются. Для анализа дополнительно выполняется
  `COUNT` его значений для текста «(N шт.)».
- POST — удаление. Для анализа СУБД удаляет значения каскадно (`ON DELETE CASCADE`), операция выполняется
  в транзакции запроса.

### 6.3.6. Удаление связанных данных

| Удаляемый объект | Что происходит со связанными данными |
| --- | --- |
| Пользователь (через `/admin/`) | удаляются все его анализы и их значения (`CASCADE`) |
| Анализ | удаляются все его значения (`CASCADE`) |
| Единица измерения (через `/admin/`) | у анализов единица становится пустой (`SET NULL`), анализы и значения сохраняются |
| Значение | связанных данных нет |

## 6.5. Коды ответов HTTP

| Код | Когда | Что видит пользователь |
| --- | --- | --- |
| 200 | страница показана; форма с ошибками показана повторно | страницу |
| 302 | успешная POST-операция; гость на закрытой странице; `/`; вход уже авторизованного пользователя | переход на другую страницу |
| 400 | заголовок `Host` не входит в `ALLOWED_HOSTS` | «Bad Request» |
| 403 | POST без корректного CSRF-токена (например, cookie браузера были очищены после открытия формы) | страницу Э11 «Форма устарела» |
| 404 | адрес не существует; объект не существует или принадлежит другому пользователю | страницу Э10 «Страница не найдена» (в режиме `DEBUG=True` вместо неё — отладочная страница Django со списком маршрутов) |
| 405 | `GET /accounts/logout/` | пустую страницу; заголовок ответа `Allow: POST, OPTIONS` |
| 503 | нет связи с сервером БД | страницу Э9 |

## 6.6. Обработка ошибок и недоступности БД

1. Подключение к PostgreSQL устанавливается при первом обращении к БД в рамках запроса; таймаут
   подключения — 5 с (`connect_timeout`).
2. Если подключиться не удалось или связь оборвалась (`OperationalError`, `InterfaceError`):
   - транзакция запроса не зафиксирована — данные не изменены;
   - `DatabaseUnavailableMiddleware` записывает в журнал сообщение «Сервер базы данных недоступен: <причина>»
     (уровень ERROR) и возвращает страницу Э9 с кодом 503;
   - страница Э9 формируется без обращения к БД (без имени пользователя и навигации).
3. Следующий запрос снова пытается подключиться; после восстановления сервера БД система работает
   без перезапуска приложения.
4. Прочие непредвиденные ошибки обрабатываются Django стандартно: код 500 (при `DEBUG=True` — отладочная страница).

## 6.7. Работа с датой и временем

| Параметр | Значение |
| --- | --- |
| Хранение в БД | `timestamptz`, UTC (`USE_TZ = True`) |
| Отображение и ввод | часовой пояс Europe/Moscow (`TIME_ZONE`), UTC+3 |
| Формат вывода даты и времени | `ДД.ММ.ГГГГ ЧЧ:ММ`, даты — `ДД.ММ.ГГГГ` |
| Формат поля ввода | `ГГГГ-ММ-ДДTЧЧ:ММ` (стандартный элемент браузера `datetime-local`; браузер показывает его в своём формате) |
| Точность | до минуты; секунды при вводе не задаются |
| «Текущий момент» для проверки даты | время сервера приложения на момент проверки формы |

## 6.8. Механизмы безопасности

| Механизм | Реализация |
| --- | --- |
| Хранение паролей | хеш PBKDF2-SHA256 с солью, 1 000 000 итераций (формат `pbkdf2_sha256$...` в `auth_user.password`) |
| Сессия | запись в `django_session`, cookie `sessionid` (HttpOnly), срок 2 недели |
| CSRF | cookie `csrftoken` + скрытое поле `csrfmiddlewaretoken` в каждой POST-форме |
| XSS | автоматическое экранирование всех выводимых значений в шаблонах |
| SQL-инъекции | только ORM и параметризованные запросы |
| Clickjacking | заголовок `X-Frame-Options: DENY` |
| Разграничение данных | фильтр по владельцу во всех запросах (6.2) |
| Секреты | `SECRET_KEY` и `DB_PASSWORD` только в `.env`, файл в `.gitignore` |
| Доступ к СУБД | пользователь `userdb` без прав суперпользователя и `CREATEDB`; `pg_hba.conf` пускает только подсеть 192.168.1.0/24 с `scram-sha-256` |

## 6.9. Конфигурация

Параметры задаются переменными окружения или файлом `.env` в корне проекта (переменные окружения имеют приоритет).

| Переменная | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `SECRET_KEY` | небезопасный ключ для разработки | ключ подписи сессий и CSRF-токенов; в `.env` — случайная строка 50 символов |
| `DEBUG` | `True` | отладочный режим (подробные страницы ошибок) |
| `ALLOWED_HOSTS` | `127.0.0.1,localhost` | допустимые значения заголовка `Host` |
| `DB_NAME` | `study` | имя БД |
| `DB_USER` | `userdb` | пользователь БД |
| `DB_PASSWORD` | пусто | пароль пользователя БД |
| `DB_HOST` | `127.0.0.1` | IP сервера БД (192.168.1.7) |
| `DB_PORT` | `5432` | порт PostgreSQL |
| `DB_ENGINE` | не задана | значение `sqlite` переключает приложение на SQLite — только для запуска тестов без сервера БД |

Постоянные настройки в `settings.py`: `LANGUAGE_CODE = "ru"`, `TIME_ZONE = "Europe/Moscow"`, `USE_TZ = True`,
`ATOMIC_REQUESTS = True`, `LOGIN_URL = "login"`, `LOGIN_REDIRECT_URL = "analysis_list"`,
`LOGOUT_REDIRECT_URL = "login"`, стандартные валидаторы паролей Django.
