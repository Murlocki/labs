# 2. Функциональные требования

## 2.0. Условные обозначения и общие правила

**Приоритет требования:**

- **M** (Must) — обязательное требование;
- **S** (Should) — желательное требование;
- **C** (Could) — требование на перспективу.

**Формат описания требования:**

- *Актор* — роль, выполняющая действие (см. 1.6).
- *Точка входа* — откуда пользователь попадает к функции и какой HTTP-запрос при этом выполняется.
- *Поля* — поля формы, их обязательность, значения по умолчанию, правила проверки и тексты ошибок.
- *Основной сценарий* — нумерованная последовательность действий пользователя (П) и системы (С).
- *Альтернативные сценарии* — отклонения от основного сценария (обозначаются номером шага и буквой).
- *Результат* — состояние данных и интерфейса после успешного выполнения.

**Общие правила для всех функций:**

1. Формат даты в интерфейсе — `ДД.ММ.ГГГГ`, даты и времени — `ДД.ММ.ГГГГ ЧЧ:ММ`, часовой пояс — Europe/Moscow.
2. Все изменяющие операции выполняются только методом POST и содержат CSRF-токен.
3. После успешной POST-операции система выполняет перенаправление (HTTP 302) и показывает на следующей странице
   одноразовое сообщение об успехе (см. 6.4). Повторное обновление страницы не повторяет операцию.
4. При ошибках проверки форма показывается повторно (HTTP 200): ошибка выводится под соответствующим полем,
   поле подсвечивается красной рамкой, все введённые значения сохраняются в полях, данные в БД не изменяются.
5. Текстовые поля при сохранении очищаются от пробелов в начале и в конце; строка из одних пробелов считается пустой.
6. Все функции разделов 2.2–2.4 доступны только авторизованному пользователю (FR-4) и работают только
   с его собственными данными (FR-5).
7. Стандартное сообщение об ошибке обязательного поля: «Обязательное поле.»; превышения длины:
   «Убедитесь, что это значение содержит не более N символов (сейчас M).».

## 2.1. Регистрация, вход и разграничение доступа

Реализуется встроенной подсистемой Django `django.contrib.auth`: учётные записи хранятся в таблице `auth_user`,
сессии — в таблице `django_session`, идентификатор сессии передаётся в cookie `sessionid`.

### FR-1. Регистрация пользователя — S

- **Актор:** гость.
- **Точка входа:** ссылка «Регистрация» в шапке или на странице входа → `GET /accounts/signup/`.
- **Поля:**

  | Поле (подпись) | Обяз. | Правила | Текст ошибки |
  | --- | :---: | --- | --- |
  | Имя пользователя | да | до 150 символов; только буквы, цифры и знаки `@ . + - _` | «Введите правильное имя пользователя. Оно может содержать только буквы, цифры и знаки @/./+/-/_.» |
  | | | уникально в системе **без учёта регистра** («Kirill» и «kirill» — одно имя) | «Пользователь с таким именем уже существует.» |
  | Пароль | да | не короче 8 символов | «Введённый пароль слишком короткий. Он должен состоять из как минимум 8 символов.» |
  | | | не состоит только из цифр | «Введённый пароль состоит только из цифр.» |
  | | | не входит в список распространённых паролей | «Введённый пароль слишком широко распространён.» |
  | | | не похож на имя пользователя | «Введённый пароль слишком похож на имя пользователя.» |
  | Подтверждение пароля | да | совпадает с паролем | «Введенные пароли не совпадают.» |

  Под полями выводятся подсказки: под именем — «Обязательное поле. Не более 150 символов. Только буквы, цифры
  и символы @/./+/-/_.», под паролем — список из четырёх правил сложности, под подтверждением — «Для подтверждения
  введите, пожалуйста, пароль ещё раз.». Ошибки сложности пароля выводятся под полем «Подтверждение пароля»,
  одновременно могут выводиться несколько ошибок.

- **Основной сценарий:**
  1. П: открывает страницу регистрации.
  2. С: показывает форму с пустыми полями и ссылку «Уже есть учётная запись? Вход».
  3. П: заполняет поля и нажимает «Зарегистрироваться».
  4. С: проверяет поля по правилам таблицы.
  5. С: создаёт запись в `auth_user` (пароль сохраняется только в виде хеша PBKDF2-SHA256, признак `is_active` = true,
     `is_staff` = false), создаёт сессию (автоматический вход).
  6. С: перенаправляет на `/analyses/` и показывает сообщение «Регистрация выполнена.».
- **Альтернативные сценарии:**
  - 1а. Пользователь уже авторизован → С: сразу перенаправляет на `/analyses/`, форма не показывается.
  - 4а. Хотя бы одно правило нарушено → С: показывает форму повторно с ошибками; имя пользователя сохраняется
    в поле, поля паролей очищаются; учётная запись не создаётся.
- **Результат:** в системе новая учётная запись, пользователь авторизован и видит пустой список анализов.

### FR-2. Вход в систему — M

- **Актор:** гость.
- **Точка входа:** ссылка «Вход» в шапке; автоматическое перенаправление при обращении к закрытой странице (FR-4)
  → `GET /accounts/login/` (возможно с параметром `?next=<адрес>`).
- **Поля:** «Имя пользователя» (обязательное), «Пароль» (обязательное).
- **Основной сценарий:**
  1. П: открывает страницу входа.
  2. С: показывает форму и ссылку «Нет учётной записи? Регистрация»; значение `next` передаётся в скрытом поле.
  3. П: вводит имя и пароль, нажимает «Войти».
  4. С: ищет пользователя по имени (с учётом регистра) и сверяет хеш пароля.
  5. С: создаёт сессию, обновляет дату последнего входа (`last_login`).
  6. С: перенаправляет на адрес из `next`, если он указан и относится к этому же сайту; иначе — на `/analyses/`.
- **Альтернативные сценарии:**
  - 1а. Пользователь уже авторизован → С: перенаправляет на `/analyses/`.
  - 4а. Пользователь не найден или пароль неверен → С: показывает форму повторно с сообщением над полями
    «Неверный логин или пароль.»; введённое имя сохраняется, поле пароля очищается.
  - 4б. Учётная запись заблокирована (`is_active` = false) → С: то же сообщение «Неверный логин или пароль.»
    (система не сообщает, что учётная запись существует).
  - 6а. В `next` указан адрес другого сайта → С: игнорирует его и перенаправляет на `/analyses/`.
- **Результат:** пользователь авторизован; сессия действует 2 недели (1 209 600 с) и не завершается
  при закрытии браузера.

### FR-3. Выход из системы — M

- **Актор:** пользователь.
- **Точка входа:** кнопка «Выйти» в шапке любой страницы → `POST /accounts/logout/`.
- **Основной сценарий:**
  1. П: нажимает «Выйти».
  2. С: удаляет сессию из БД и cookie, перенаправляет на `/accounts/login/`.
- **Альтернативные сценарии:**
  - 1а. Запрос `GET /accounts/logout/` (например, ввод адреса вручную) → С: отвечает 405 (пустая страница),
    выход не выполняется.
- **Результат:** пользователь стал гостем; при переходе по закрытым адресам срабатывает FR-4.

### FR-4. Ограничение доступа для гостей — M

- Все страницы, кроме `/accounts/login/` и `/accounts/signup/`, доступны только авторизованному пользователю.
- При обращении гостя к закрытой странице система перенаправляет его на `/accounts/login/?next=<исходный адрес>`.
  После успешного входа (FR-2) пользователь попадает на исходную страницу.
- Для гостя в шапке выводятся только ссылки «Вход» и «Регистрация».

### FR-5. Разграничение данных пользователей — M

- Каждый анализ принадлежит одному пользователю (владельцу); значение анализа принадлежит владельцу анализа.
- Все выборки анализов и значений ограничиваются условием «владелец = текущий пользователь»:
  списки, выпадающие списки в формах, страницы просмотра, изменения и удаления.
- Обращение к анализу или значению другого пользователя (по прямому адресу, по идентификатору в форме)
  обрабатывается так, будто объекта не существует: ответ **404**, страница «Страница не найдена» (Э10);
  данные не изменяются.
- Попытка при отправке формы значения указать чужой анализ (подмена идентификатора) отклоняется ошибкой поля
  «Выберите корректный вариант. Вашего варианта нет среди допустимых значений.».
- Администратор работает с данными всех пользователей только через административный интерфейс (раздел 2.5).

## 2.2. Анализы

### FR-6. Просмотр списка анализов — M

- **Актор:** пользователь.
- **Точка входа:** ссылка «Мои анализы» или название системы в шапке; адрес `/` (перенаправляет сюда)
  → `GET /analyses/`.
- **Основной сценарий:**
  1. П: открывает страницу.
  2. С: выбирает из БД все анализы текущего пользователя вместе с единицей измерения и количеством значений
     (одним SQL-запросом с агрегатом `COUNT`), сортирует по названию по алфавиту.
  3. С: показывает заголовок «Мои анализы», кнопку «+ Добавить анализ», строку поиска (FR-7) и таблицу:

     | Столбец | Содержимое |
     | --- | --- |
     | Название | название анализа — ссылка на страницу анализа (FR-9) |
     | Ед. изм. | обозначение единицы или «—», если единица не указана |
     | Значений | количество значений анализа, выравнивание по правому краю |
     | Действия | ссылки «Изменить» (FR-10) и «Удалить» (FR-11, красным) |

- **Альтернативные сценарии:**
  - 2а. У пользователя нет анализов → С: вместо таблицы показывает блок «У вас пока нет анализов.»
    и ссылку «Добавить анализ».
- **Результат:** пользователь видит актуальное состояние своих анализов; данные читаются из БД при каждом открытии.

### FR-7. Поиск анализа по названию — S

- **Точка входа:** строка поиска «Поиск по названию» и кнопка «Найти» на странице списка → `GET /analyses/?q=<строка>`.
- **Правила:**
  - строка поиска очищается от пробелов по краям; пустая строка — показ всех анализов;
  - анализ попадает в результат, если его название **содержит** строку поиска, без учёта регистра
    («глю» находит «Глюкоза»);
  - введённая строка остаётся в поле поиска после выполнения;
  - сортировка и столбцы — как в FR-6.
- **Альтернативные сценарии:**
  - Ничего не найдено → С: блок «Ничего не найдено.» и ссылка «Сбросить поиск» (ведёт на `/analyses/`).

### FR-8. Создание анализа — M

- **Актор:** пользователь.
- **Точка входа:** кнопка «+ Добавить анализ» на странице списка → `GET /analyses/add/`.
- **Поля:**

  | Поле (подпись) | Элемент | Обяз. | По умолчанию | Правила и ошибки |
  | --- | --- | :---: | --- | --- |
  | Название | текстовое поле | да | пусто | 1–128 символов после удаления пробелов по краям. Уникально среди анализов пользователя без учёта регистра, иначе — «Анализ с таким названием уже существует.» |
  | Единица измерения | выпадающий список | нет | «— не указана —» | значения — все единицы справочника (FR-17), по алфавиту |
  | Описание | многострочное поле (4 строки) | нет | пусто | до 2000 символов; переносы строк сохраняются |

- **Основной сценарий:**
  1. П: открывает форму «Новый анализ».
  2. П: заполняет поля, нажимает «Сохранить».
  3. С: проверяет поля; проверяет, что у пользователя нет анализа с таким же названием без учёта регистра.
  4. С: сохраняет анализ с владельцем = текущий пользователь, датой создания = текущий момент.
  5. С: перенаправляет на страницу созданного анализа (FR-9) с сообщением «Анализ добавлен.».
- **Альтернативные сценарии:**
  - 2а. П нажимает «Отмена» → С: возвращает на `/analyses/` без сохранения.
  - 3а. Ошибки проверки → форма показывается повторно (общее правило 4).
  - 3б. Анализ с таким же названием есть у **другого** пользователя → ошибки нет, анализ создаётся.
- **Результат:** в БД новая запись `analyses_analysis`; в списке анализов она показывается с количеством значений 0.

### FR-9. Просмотр анализа — M

- **Точка входа:** ссылка-название в списке анализов; перенаправление после создания, изменения анализа
  и операций со значениями → `GET /analyses/<id>/`.
- **Содержимое страницы:**
  - ссылка «← Мои анализы»;
  - карточка анализа: заголовок — название; «Единица измерения» (или «—»); «Описание» (с сохранением
    переносов строк или «—»); «Создан» — дата создания `ДД.ММ.ГГГГ`;
  - кнопки «Изменить анализ» (FR-10), «Удалить анализ» (FR-11, красная), «+ Добавить значение» (FR-13);
  - раздел «Значения» с таблицей значений (FR-12).
- **Альтернативные сценарии:** анализ не существует или принадлежит другому пользователю → 404 (FR-5).

### FR-10. Изменение анализа — M

- **Точка входа:** «Изменить» в списке анализов или «Изменить анализ» на странице анализа → `GET /analyses/<id>/edit/`.
- **Поля и проверки:** как в FR-8; форма «Изменение анализа» открывается заполненной текущими значениями.
  При проверке уникальности название самого изменяемого анализа не учитывается (можно сохранить без изменений
  или изменить только регистр букв).
- **Основной сценарий:** П изменяет поля и нажимает «Сохранить» → С сохраняет изменения, обновляет дату изменения,
  перенаправляет на страницу анализа с сообщением «Анализ изменён.».
- **Альтернативные сценарии:** «Отмена» → возврат на страницу анализа без сохранения; ошибки проверки —
  общее правило 4; чужой или несуществующий анализ — 404.
- **Результат:** новые данные анализа отображаются в списке, на странице анализа и во всех его значениях
  (единица измерения значений берётся из анализа).

### FR-11. Удаление анализа — M

- **Точка входа:** «Удалить» в списке или «Удалить анализ» на странице анализа → `GET /analyses/<id>/delete/`.
- **Основной сценарий:**
  1. С: показывает страницу подтверждения: заголовок «Удалить анализ «<название>»?», текст
     «Будут также удалены все значения этого анализа (N шт.).», предупреждение «Действие необратимо.»,
     кнопки «Удалить» (красная) и «Отмена».
  2. П: нажимает «Удалить» → `POST /analyses/<id>/delete/`.
  3. С: в одной транзакции удаляет анализ и все его значения (каскадно).
  4. С: перенаправляет на `/analyses/` с сообщением «Анализ удалён.».
- **Альтернативные сценарии:** «Отмена» → возврат на страницу анализа; чужой или несуществующий анализ — 404,
  данные не удаляются.
- **Результат:** анализа и его значений нет в БД и в списке.

## 2.3. Значения анализа

### FR-12. Просмотр значений анализа — M

- **Место:** раздел «Значения» на странице анализа (FR-9).
- **Таблица:**

  | Столбец | Содержимое |
  | --- | --- |
  | Дата и время | дата и время сдачи `ДД.ММ.ГГГГ ЧЧ:ММ` |
  | Значение | значение (жирным) и через пробел единица измерения анализа, если она указана |
  | Комментарий | комментарий или пусто |
  | Действия | ссылки «Изменить» (FR-14) и «Удалить» (FR-15, красным) |

- **Сортировка:** по дате и времени сдачи, новые сверху.
- **Постраничный вывод:** по 50 значений на страницу, номер страницы передаётся параметром `?page=N`.
  - Если значений не больше 50, навигация не выводится.
  - Если больше — под таблицей выводится строка навигации: «← Новее» (нет на первой странице),
    «Страница N из M · всего значений: K», «Старее →» (нет на последней странице).
  - Нечисловое значение `page` → показывается первая страница; номер больше последнего → последняя страница.
- **Пустая таблица:** блок «Значений пока нет.» и ссылка «Добавить значение».

### FR-13. Добавление значения анализа — M

- **Точки входа:**
  - кнопка «+ Добавить значение» на странице анализа → `GET /analyses/<id>/values/add/`; поле «Анализ»
    заранее заполнено этим анализом;
  - ссылка «+ Добавить значение» в шапке → `GET /values/add/`; анализ выбирается из списка.
- **Поля:**

  | Поле (подпись) | Элемент | Обяз. | По умолчанию | Правила и ошибки |
  | --- | --- | :---: | --- | --- |
  | Анализ | выпадающий список | да | «— выберите анализ —» или анализ из адреса | только анализы текущего пользователя, по алфавиту; чужой или несуществующий — «Выберите корректный вариант. Вашего варианта нет среди допустимых значений.» |
  | Значение | текстовое поле | да | пусто | 1–64 символа после удаления пробелов по краям; любой текст (FR-16) |
  | Дата и время сдачи | поле даты и времени (календарь браузера) | да | текущие дата и время с точностью до минуты | корректная дата — иначе «Введите правильную дату и время.»; не позже текущего момента — иначе «Дата сдачи не может быть в будущем.» |
  | Комментарий | текстовое поле | нет | пусто | до 255 символов |

- **Основной сценарий:**
  1. П: открывает форму «Новое значение».
  2. П: заполняет поля, нажимает «Сохранить».
  3. С: проверяет поля, переводит дату из часового пояса Europe/Moscow в UTC и сохраняет значение.
  4. С: перенаправляет на страницу выбранного анализа с сообщением «Значение добавлено.»; новое значение
     занимает место в таблице согласно дате сдачи.
- **Альтернативные сценарии:**
  - 1а. У пользователя нет ни одного анализа → С: вместо формы показывает «Сначала создайте анализ, к которому
    будет относиться значение.» и ссылку «Добавить анализ».
  - 1б. В адресе `/analyses/<id>/values/add/` указан чужой или несуществующий анализ → 404.
  - 2а. «Отмена» → возврат на страницу анализа (если форма открыта со страницы анализа) или на `/analyses/`.
  - 3а. Ошибки проверки — общее правило 4.
- **Результат:** в БД новая запись `analyses_analysisvalue`; количество значений анализа в списке увеличилось на 1.

### FR-14. Изменение значения анализа — M

- **Точка входа:** «Изменить» в строке таблицы значений → `GET /values/<id>/edit/`.
- **Поля и проверки:** как в FR-13; форма «Изменение значения» открывается заполненной текущими данными.
  Анализ можно сменить на другой анализ того же пользователя — значение переносится в него.
- **Основной сценарий:** П изменяет поля, нажимает «Сохранить» → С сохраняет, перенаправляет на страницу
  анализа, к которому значение относится **после** изменения, с сообщением «Значение изменено.».
- **Альтернативные сценарии:** «Отмена» → страница анализа; чужое или несуществующее значение — 404.

### FR-15. Удаление значения анализа — M

- **Точка входа:** «Удалить» в строке таблицы значений → `GET /values/<id>/delete/`.
- **Основной сценарий:**
  1. С: показывает страницу подтверждения: заголовок «Удалить значение <значение> <единица> от <ДД.ММ.ГГГГ ЧЧ:ММ>?»
     (например, «Удалить значение 5.4 ммоль/л от 27.09.2026 10:30?»), строку «Анализ: «<название>».»,
     предупреждение «Действие необратимо.», кнопки «Удалить» и «Отмена».
  2. П: нажимает «Удалить» → `POST /values/<id>/delete/`.
  3. С: удаляет значение, перенаправляет на страницу анализа с сообщением «Значение удалено.».
- **Альтернативные сценарии:** «Отмена» → страница анализа; чужое или несуществующее значение — 404.

### FR-16. Хранение нечисловых значений — M

- Значение хранится как строка до 64 символов и выводится без изменений: «5.4», «120/80», «< 0.5»,
  «отрицательно», «не обнаружено».
- Система не выполняет с значениями арифметических операций, не округляет и не переводит единицы измерения.
- Десятичный разделитель не нормализуется: «5.4» и «5,4» сохраняются так, как введены.

## 2.4. Справочник единиц измерения

### FR-17. Справочник единиц измерения — M

- Справочник общий для всех пользователей, хранится в таблице `analyses_unit`.
- При установке (выполнении миграций) справочник заполняется 18 единицами (раздел 4.6); повторное выполнение
  не создаёт дубликатов.
- Пользователи справочник только читают (выбор в форме анализа); изменяет его администратор (FR-21).

### FR-18. Выбор единицы измерения анализа — M

- В формах создания и изменения анализа единица выбирается из выпадающего списка, отсортированного по алфавиту;
  первый пункт — «— не указана —» (пустое значение).
- Единица относится к анализу и выводится рядом со всеми его значениями.
- При удалении единицы администратором у анализов, которые её использовали, единица становится «—»;
  сами анализы и их значения сохраняются.

## 2.5. Администрирование

Реализуется встроенным модулем `django.contrib.admin` по адресу `/admin/`. Заголовок интерфейса —
«MedTracker — администрирование», язык — русский.

### FR-19. Доступ к административному интерфейсу — M

- Вход в `/admin/` разрешён только пользователям с признаком «Статус персонала» (`is_staff`);
  собственная страница входа — `/admin/login/`.
- Неавторизованный пользователь и пользователь без `is_staff` перенаправляются на `/admin/login/`
  и не могут войти.
- Первый администратор создаётся командой `python manage.py createsuperuser`.
- Для администратора в шапке пользовательских страниц выводится ссылка «Администрирование».

### FR-20. Управление пользователями — M

- Раздел «Пользователи»: список с поиском по имени пользователя и фильтрами «Статус персонала»,
  «Статус суперпользователя», «Активный», «Группы».
- Создание пользователя (имя и пароль), изменение данных, смена пароля.
- Блокировка — снятие флажка «Активный»: пользователь не может войти (FR-2, альтернатива 4б), его данные сохраняются.
- Удаление пользователя удаляет все его анализы и значения (каскадно) после подтверждения на странице,
  перечисляющей удаляемые объекты.

### FR-21. Управление справочником единиц измерения — M

- Раздел «Единицы измерения»: список (обозначение, категория), фильтр по категории, поиск по обозначению.
- Создание, изменение и удаление единиц; обозначение уникально — при дубликате выводится ошибка поля.

### FR-22. Управление анализами и значениями всех пользователей — S

- Раздел «Анализы»: столбцы «название», «владелец», «единица измерения», «создан»; фильтры по владельцу
  и единице; поиск по названию. На странице анализа — встроенная таблица его значений для просмотра и правки.
- Раздел «Значения анализов»: столбцы «анализ», «владелец», «значение», «дата и время сдачи», «комментарий»;
  фильтры по владельцу и дате сдачи; навигация по датам сдачи (год → месяц → день); поиск по названию анализа,
  значению и комментарию.
- Любую запись можно изменить или удалить; действия фиксируются в журнале `django_admin_log`.

## 2.6. Общие требования к обработке данных

### FR-23. Сохранение данных — M

- Все данные хранятся в БД PostgreSQL; обращения к БД выполняются только через Django ORM.
- Каждый HTTP-запрос выполняется в одной транзакции: при ошибке на любом шаге все изменения этого запроса
  отменяются (частичное сохранение невозможно).

### FR-24. Обработка форм — M

- Формы отправляются методом POST с CSRF-токеном; запрос без корректного токена отклоняется с ответом 403
  и страницей «Форма устарела» (Э11), данные не сохраняются.
- После успешной обработки — перенаправление (POST → Redirect → GET) и одноразовое сообщение об успехе
  зелёного цвета вверху следующей страницы; при обновлении страницы сообщение больше не показывается.
- При ошибках — общее правило 4 (раздел 2.0).
- Обязательные поля отмечены красной звёздочкой `*` после подписи.

### FR-25. Навигация — M

- Шапка каждой пользовательской страницы:
  - слева — название «MedTracker» (ссылка на `/analyses/`);
  - для пользователя — ссылки «Мои анализы», «+ Добавить значение», для администратора дополнительно
    «Администрирование»;
  - справа — имя текущего пользователя и кнопка «Выйти»; для гостя — ссылки «Вход» и «Регистрация».
- Адрес `/` перенаправляет на `/analyses/` (для гостя — далее на страницу входа по FR-4).
- Переходы между страницами — см. схему 5.4.

## 2.8. Сквозной сценарий: добавление значения анализа

```text
Пользователь входит через /accounts/login/                      (FR-2)
    ↓ создаётся сессия
Открывает /analyses/ → выбирает «Глюкоза»                         (FR-6, FR-9)
    ↓
Нажимает «+ Добавить значение» → /analyses/3/values/add/          (FR-13)
    ↓ вводит 5.4, дату 27.09.2026 08:30, комментарий «натощак»
    ↓ POST (CSRF-токен)
View: проверка авторизации и владельца → валидация формы          (FR-4, FR-5, FR-24)
    ↓ ORM: INSERT в одной транзакции
PostgreSQL: INSERT INTO analyses_analysisvalue                     (FR-23)
    ↓ redirect 302
/analyses/3/ → «Значение добавлено.»; строка «27.09.2026 08:30 | 5.4 ммоль/л | натощак»
```
